# Plan: GV-001 to GV-020

Fixes for the twenty gaps filed in `docs/bugs.md` against phases 0–16. Each entry there now says what changed and in
which commit; this page records the approach, the tests and what is left for the owner.

## Approach
1. **Small UI and text fixes first** (GV-004, 010, 011, 014–017, 019, 020): ViewModel properties with tests, XAML
   bound to them, sample data that shows them (`--sample-data` now has two unknown homebrew games to edit).
2. **Settings plumbing** (GV-005, 009, 012): an `IConfirmationService` (ContentDialog in the app, a fixed answer in
   sample data and tests), `IGameFilePicker.PickSystemFileAsync`, and an opt-in save location in `BatterySaveStore`.
3. **New core devices** (GV-013): `PowerPad` and `ArkanoidPaddle` behind `IInputDevice`, tests first for their serial
   protocols and state round-trips (NES state version 4).
4. **Input** (GV-001, 002, 003, 018): one action catalog per system in `GameVault.ViewModels` (names and defaults),
   remaps as JSON in settings, applied by `ControllerManager`; the per-system keyboard special cases move into
   `KeyboardMapping.ForLayout`. A Platform test checks every default the catalog shows against the real bindings, so
   they can't drift apart. The port cards become a shared `ControllerPortsPanel` used by Settings and the Player.
5. **Data** (GV-006, 007, 008): only facts with a primary source. Hashes come from No-Intro's headerless NES DAT;
   RAM facts from public disassemblies; homebrew only under licenses that allow redistribution, checked file by file.
   Sources are in `docs/gamedb-sources.md`, `data/homebrew/*/README.md` and `THIRD-PARTY-NOTICES.md`.
6. **Docs**: `docs/design/input.md` §6.7–6.8 and §9, `docs/compatibility.md`, the data READMEs, and the user manual
   (edition 3).

## Tests added
- ViewModels: Game Details per-system properties and unknown-game details; confirmations (cancel keeps the item);
  Choose… pickers; overscan amount; the remap set (conflicts, per game, per model, presets, JSON) and the Remap…
  editor (key capture, reserved keys, pad capture); four-player assignment and swaps; the Player's Controllers and
  Challenges visibility.
- Platform: rewind scrubbing both ways and continuing from the chosen point; the Disk II notice; saves next to the
  game file; the overscan crop amount; Power Pad keys and the paddle through the host; every remap default against
  the keyboard and pads; keyboard and pad remaps per layout, game, model and player; capture mode; the bundled
  homebrew in the library.
- Core: Power Pad and Arkanoid serial order, the paddle's range, and save-state round-trips.
- Library: every bundled game data file loads; accessory profiles, Metroid's password and the SMB/Zelda maps read
  what their sources say; every bundled homebrew game has a license and runs; unknown-game details are stored.

## Left for the owner
- **Build and look at the WinUI app on Windows.** The XAML changed (Settings, Game Details, Player, two new user
  controls) and can't be compiled on Linux; the ViewModels behind it are tested.
- **Check the shipped game data on real cartridges** (Phase 6 and 9 owner checklists): Metroid's password capture,
  the three memory maps, and a few accessory games (a Zapper game, a Four Score game, World Class Track Meet on the
  keyboard mat, Arkanoid with the mouse). Choose the other password launch titles.
- Run-ahead safety and sprite-limit flags per game need testing with the games, so none ship yet.

## Known limits
- Remapping covers buttons; the analog sticks and triggers keep their roles.
- The Power Pad and the paddle aren't carried over netplay (netplay sends controller states only), like the Zapper.
- With **Two players, one keyboard** on, Remap… lists the standard keys for Player 1 (Z, X…) and none for Player 2,
  although the preset's keys are what's in effect until a button is remapped; remapping works either way.
