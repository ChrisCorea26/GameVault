# Phase 2 — PPU + NROM

**Goal (SPEC §12):** PPU, mapper 0, Win2D video in `GameView`, keyboard input.

**Done when:** NROM test ROMs render correctly; golden-image tests pass.

## Core

### `Ppu/Ppu2C02` (replaces `PpuTimingStub`)
Dot-based, following NESdev Wiki "PPU rendering", "PPU scrolling", "PPU sprite evaluation" and
"PPU frame timing":
- **Registers** `$2000–$2007`, mirrored to `$3FFF`. The I/O latch (open bus) decays per bit after about
  600 ms without a refresh. Write toggle `w`. `$2007` reads are buffered, except palette reads.
  `$2007` access during rendering performs the coarse-X/Y increment glitch.
- **Scrolling**: the loopy `v/t/x/w` model, with increments at dots 8…256 / 328 / 336, the copies at dot 257,
  and dots 280–304 of the pre-render line.
- **Background**: NT/AT/pattern fetches every 8 dots into 16-bit shift registers, and the left-8 mask.
- **Sprites**: per-dot secondary-OAM evaluation on dots 65–256, including the sprite-overflow hardware
  bug. Pattern fetches on dots 257–320, and 8 sprite units with X counters and priority.
  Sprite 0 hit has the dot 255 and left-clip rules.
  - An optional **"remove sprite limit"** mode renders more than 8 sprites per line without changing the
    overflow flag or the timing.
- **Timing**: VBlank set at dot 1 of line 241, with the `$2002` read race (suppressing the flag and NMI).
  NMI is enabled while in VBlank, and the odd-frame dot is skipped when rendering is on.
- **Output**: a 256×240 `ushort` framebuffer of palette index (6 bits) | emphasis (3 bits). Grayscale is
  applied to the index. When rendering is off, the backdrop shows, or the palette entry `v` points at.
- **Memory**: CIRAM (2 KB, 4 KB for four-screen) laid out by the mapper's mirroring. Palette RAM has its
  `$3F10/14/18/1C` mirrors. Pattern fetches go through `IMapper.PpuRead`. An A12 rising edge calls
  `IMapper.OnA12Rise`.
- **Phase alignment**: CPU reads and writes land part-way through the CPU cycle (NESdev "Cycle reference
  chart"). The bus advances the PPU before and after each access by a split of the master clocks, so
  `$2002`/NMI races can be timed to the exact dot.

### `Input/StandardController` (per [`docs/design/input.md`](../design/input.md) §2)
- `$4016` strobe, serial reads, and `$4017` for player 2. Unused bits read as open bus. `IStateful`.
- The core sees only one `ControllerState` byte per port, in shift order: A, B, Select, Start, Up, Down,
  Left, Right.
- `NesConsole.SetControllerState(port, state)` is called between frames through the host's command
  queue. Device identity, merging and the opposite-direction rule stay in the platform layer, so the
  core stays deterministic and the input stream can be recorded.

### `Ppu/NtscPalette`
Generated by our own implementation of the 2C02 composite signal levels (NESdev Wiki "NTSC video"):
64 colors × 8 emphasis combinations, as ARGB. Generated code means no third-party palette file is needed.

## Tests
- **Unit**: register behavior, `v/t/x/w` updates, palette mirroring and the grayscale mask, `$2007`
  buffering, OAM DMA into OAM, and PPU and controller state round-trips.
- **Input** (input.md §12):
  - **Core:** a `$4016` strobe/read test checks the bit order.
  - **Platform:** OR merging across sources, the opposite-direction rule with and without the setting,
    focus release, and that hotkeys never reach the game.
- **Test ROMs** (downloaded, NROM only):
  - `$6000` protocol: `ppu_vbl_nmi` single-test ROMs 01–10, `ppu_open_bus`, `oam_read`.
  - `$F8` result code after a fixed number of frames (old blargg suites): `sprite_hit_tests_2005.10.05`
    (11 tests), `sprite_overflow_tests` (5 tests), and `blargg_ppu_tests_2005.09.15b`
    (palette_ram, sprite_ram, vbl_clear_time, vram_access).
    - `power_up_palette` expects one specific console's power-up palette, so it is listed as informational.
- **Golden images**: hash the indexed framebuffer at a fixed frame for the nestest menu and each blargg
  result screen, and compare against hashes committed in `tests/GameVault.Core.Tests/Golden/golden.json`.
  - On a mismatch, the test writes the actual frame as a PNG to the test output folder.
  - I check each new golden image by eye (rendered through `NtscPalette`) before committing its hash.
- `test_ppu_read_buffer` (mapper 3) and the combined ROMs (MMC1) move to Phase 4 with their mappers.

## Platform
- `Video/TripleBuffer<T>`: lock-free handoff from the emulation thread to the renderer. The writer never
  blocks. The reader always gets the newest complete frame.
- `Video/FrameSink : IVideoSink`: copies each finished frame into the triple buffer and signals the renderer.
- `Emulation/EmulatorHost`: owns the emulation thread and the `NesConsole`. A thread-safe command queue
  (load, pause, resume, reset, stop) is processed between frames.
  - Frames are paced at 60.0988 Hz with a high-resolution timer. Audio becomes the master clock in Phase 3.
  - Implements `IEmulatorService` from ViewModels.
- `Input/` implements the Phase 2 rows of [`docs/design/input.md`](../design/input.md) §11:
  - `KeyboardMapping`: the §4.1 defaults on Player 1 (arrows, Z = B, X = A, Enter = Start, Right Shift
    = Select). Player 2 has no default keyboard binding (§4.2). Keys are Windows virtual-key codes
    (ints), so the mapping is testable without WinUI.
  - The §8 hotkeys (Esc, Backspace, Tab, F5, F8, F12) never reach the game. In Phase 2, Esc pauses.
  - `InputService`: tracks held keys per source, ORs sources per port, and applies the
    opposite-direction rule (§6): the most recently pressed direction on each axis wins, unless
    `AppSettings.AllowOppositeDirections` is set.
  - `ReleaseAll()` releases every held key when the game view loses focus or the window deactivates
    (§4.4).
  - The host samples the input service as late as possible before each frame and posts one byte per
    port (§2).

## ViewModels
- `IEmulatorService` (state, load, pause/resume, reset, stop, errors) and `IGameFilePicker`.
- `PlayerViewModel`: title, running/paused state, pause/reset commands, and plain-language errors. For
  example, "This game needs a cartridge type GameVault doesn't support yet (mapper 4)".
- `LibraryViewModel`: an **Open game file** command, which picks a `.nes` file and navigates to the Player.
- Sample data: `SampleEmulatorService` produces an animated test pattern, so the Player renders under
  `--sample-data` with no ROM.

## App
- `Controls/GameView`: a templated control (style in `Themes/Generic.xaml`) hosting a Win2D
  `CanvasSwapChainPanel`.
  - Its render thread waits for new frames, converts indices to BGRA, and draws with nearest-neighbor
    integer scaling. The default crop hides the top and bottom 8 lines.
  - Its `KeyDown`/`KeyUp` handlers only forward to the platform input service; they contain no logic
    (input.md §10). Losing focus calls `ReleaseAll()`.
  - It creates the swap chain in `Loaded` and tears it down in `Unloaded`. Nothing heavy happens in the
    constructor.
- `Views/PlayerPage`: the `GameView` plus a minimal top bar (pause, reset, back). Fullscreen and the overlay
  polish come in later phases.
- `Services/WinUiGameFilePicker`: `Microsoft.Windows.Storage.Pickers.FileOpenPicker`, which works for
  unpackaged apps.
- `--page=player` launch argument: CI's smoke test uses it to open the Player under `--sample-data`, which
  exercises Win2D and the swap chain.

## Out of scope
APU, audio, SDL controllers, port assignment, hot-plug, turbo, the two-player keyboard preset and
Settings → Input (Phase 3, per input.md §11). Other mappers, save states in the UI, and D3D11 presets
(Phase 4). Library scanning (Phase 5).
